Deliverable 2 of 2: Privacy and Insider-Threat Security Report

Lanai Lifestyle: Privacy, Insider-Threat, and Security Review

A code-level audit of how client data is protected at rest, in transit, and from the people who already have legitimate access, with concrete mitigations and a build plan for encryption, two-factor auth, OTP step-up, and role-based access control.

Scope: lanai-portal + lanai_ai codebase, production config Date: 8 August 2026 Method: Static code audit + config review Vectors analysed: 13 insider threats

Executive summary

The platform has solid foundations: SOPS-encrypted production secrets, Caddy HSTS with APISIX TLS at the edge, bcrypt-hashed member PINs, a local Ollama model for AI so client data does not leave the perimeter, and no PII in logs. However, the insider-threat surface is wide. A single junior-advisor credential can enumerate the entire member base, read every member's private messages, download any member's passport and visa documents, and pull churn and lifetime-value intelligence on every client, all with no audit trail written. There is no two-factor authentication, no encryption of PII at rest, and the document vault has a broken object-level authorization check that lets any logged-in user fetch any file.

Insider-threat vectors (13)

Each vector is a realistic path for a malicious or negligent insider who already holds a legitimate account. The root cause is shared: authorization is a single coarse check ("any advisor may manage the platform"), with no per-member relationship tuples, and the audit log is effectively empty.

Critical

IT-1 · Audit logging is effectively absent

A writeAudit() helper exists but is called from exactly one place in the entire server (member-preferences update). Login, logout, role promotion, member and client creation, document upload, conversation reads, AI insight access, commission changes, and every hard-delete write no audit record. After-the-fact incident response is impossible because the trail does not exist.

Fix: Wire writeAudit into a tRPC mutation middleware so it cannot be skipped. Populate the ipAddress and userAgent columns the schema already defines.
High

IT-2 · Audit logs are not tamper-evident

The audit_logs table is a plain insertable table with no hash chain, no signed rows, and no trigger preventing update or delete. An admin with a SQL console can DELETE FROM audit_logs and leave no trace. The role that reads logs is the same role most able to suppress them.

Fix: Make the table append-only (revoke update and delete from the app role), hash-chain each row to the previous, and stream a copy to WORM storage or the lakehouse.
Critical

IT-3 · Any advisor can enumerate and read PII for every member

members.list is a protected procedure that returns email, name, phone, and nationality for all members with no assignedAdvisorId filter. The code comment even says "any advisor can view." A junior advisor calls it once and walks away with the full client roster. The same gap exists on advisors.list, clients.list, and pendingInvites.

Fix: Filter by assignedAdvisorId = ctx.user.id for the advisor role; allow senior advisors and admins to see all only with an audit entry.
Critical

IT-4 · CRM proxy exposes the full Twenty CRM API to any advisor

The /crm/* proxy forwards any request to Twenty CRM with the server's global API token. Unlike the Chatwoot proxy, there is no allowlist. An advisor can page through /crm/rest/20/people and download the entire CRM dataset, not just Lanai members, using Lanai's credential. Nothing is logged.

Fix: Port the Chatwoot allowlist pattern to the CRM proxy. Restrict to read-only, allowlisted paths, scoped to the advisor's records, and log every proxied call.
Critical

IT-5 · Document vault serves any file to any authenticated user

/manus-storage/* is guarded only by "any authenticated user." It presigns a download URL for any key with no ownership check. Permify ownership tuples are written at upload but never consulted at download. An advisor (or a member) can enumerate document keys and download other members' passports, visas, and IDs. The key suffix is only 8 hex characters, so enumeration is feasible.

Fix: Before presigning, resolve the key to a document row and call Permify.check(subject, "view", "document:id"). Log every download.
High

IT-6 · AI intelligence leaks a full dossier on any member

The intelligence endpoints accept any memberId and ship the member's full profile, preferences, requests, bookings, and proposals to the LLM with no assignment check. A junior advisor passes any member ID and receives churn risk, upsell opportunities, and the preference dossier for members they do not own.

Fix: Add a member-resource Permify relation and check it before memberFacts. Restrict to assigned advisors and log each call.
High

IT-7 · AI insights are globally readable

aiInsights.list accepts memberId and insightType inputs but never uses them in the WHERE clause, returning the 100 most recent churn-risk and upsell signals across the whole member base to any advisor.

Fix: Apply WHERE memberId IN (assigned members) for the advisor role and honour the input filter.
Critical

IT-8 · Communication hub exposes every member's messages

The communication hub returns the full timeline (email, WhatsApp, call transcriptions, portal messages, internal notes) for any member ID. messaging.getMessages takes any conversation ID and returns its messages with no ownership check. The Chatwoot proxy lets any advisor call contacts, conversations, and reports across the whole account. Private communications and transcriptions are fully exposed.

Fix: Scope all communication reads by assigned advisor. Gate getMessages with a Permify check on the conversation's member. Restrict the Chatwoot proxy to the advisor's inboxes and log access.
High

IT-9 · Member sessions are unbound and PIN brute-force is weakly throttled

Member session tokens store no IP or user agent, so a stolen cookie is reusable from anywhere. Throttling is IP-based (20 per 15 minutes), trivially bypassed by rotating IPs, with no per-account lockout on a 6-digit PIN (one million combinations). Tier changes do not invalidate sessions.

Fix: Store IP and user agent on sessions and bind validation to a hash of them. Add per-account lockout after N failed attempts. Rotate the token on tier change.
High

IT-10 · Hard-delete with no soft-delete and no audit

Several procedures issue hard DELETE with no recoverable tombstone and no audit entry: clients.remove, proposalItems.remove, celebration and family-member deletes, member-tag deletes. A disgruntled advisor can permanently destroy high-value records before quarter-end with no trail.

Fix: Replace hard deletes with a deletedAt soft-delete column enforced by Drizzle middleware. Gate hard-delete behind senior advisor plus audit, and record deletedByUserId.
High

IT-11 · Admin powers lack separation of duties

An admin can promote another account to admin with no second approver, no cooldown, and no step-up authentication. Admins exclusively read audit logs, so a compromised admin can act and then suppress evidence. There is no two-person rule and no break-glass alerting.

Fix: Require two-admin approval for role elevation. Add step-up re-authentication for admin procedures. Split "audit reader" from "admin" so admins cannot read their own logs without a separate role. Alert on every admin action.
Medium

IT-12 · Invitation token and member email shipped to the lakehouse

acceptInvite emits a domain event whose payload includes the one-time invitationToken, and member create emits the member email. The outbox delivers these to the lakehouse, widening the circle of people who could redeem an invitation and creating a parallel PII store outside the app's access controls.

Fix: Never include secrets in event payloads; emit invitationAccepted: true only. Apply a PII-redaction layer in the outbox before lakehouse insert.
Medium

IT-13 · Sensitive data in AI inference metadata and logs

The AI routes store the full LLM output (client profile, churn risk, preferences) in ai_inference_runs.outputMetadata, and the communication hub passes full message bodies and transcriptions into the AI prompt. An insider with read access to that table or the container logs can reconstruct member dossiers and private messages, bypassing application controls entirely.

Fix: Store only digests of LLM input and output, not raw objects. Route logs through a sanitiser that strips email, phone, and PIN patterns before stdout or the lakehouse.

Encryption and data protection

Critical

E-1 · No encryption at rest for PII

There is no pgcrypto, no column-level encryption, and no application cipher anywhere. Passport numbers, passport expiry, date of birth, dietary and accessibility needs, emergency contacts, family-office contacts, visa expiry, and NDA status are all stored as plaintext. A database dump or direct read exposes every piece of sensitive PII in cleartext.

Fix: Enable pgcrypto and store sensitive columns via pgp_sym_encrypt / pgp_sym_decrypt, or use app-level AES-256-GCM with a key held in a KMS. Restrict with column GRANTs.
High

E-2 · Document contents are not encrypted

Documents are PUT to S3 as raw bytes; confidentiality depends entirely on unverified bucket SSE settings on the Forge backend. Combined with IT-5, this means passports and visas are both unencrypted at rest and downloadable by anyone logged in.

Fix: Encrypt with AES-GCM before upload (envelope key from KMS), or enforce and verify SSE-KMS on the bucket and document it.
High

E-3 · No database backup mechanism

No pg_dump, WAL-G, Barman, or Velero configuration exists anywhere. MinIO is deployed but only as app object storage. There is no backup, encrypted or otherwise, and no tested restore path.

Fix: Add WAL-G or Barman with a KMS-encrypted S3 target and test a restore on a regular schedule.
High

E-4 · Latent external LLM egress to forge.manus.im

The active AI features use local Ollama, which is good. However llm.ts has a hardcoded fallback to https://forge.manus.im/v1/chat/completions when BUILT_IN_FORGE_API_URL is unset. If that env var is ever empty, member prompts and data egress to a third party.

Fix: Remove the external fallback and fail fast if the in-perimeter endpoint is unset. Add an egress network policy allowlist.
Medium

E-5 · No TLS on internal traffic and sslmode disabled

The edge has TLS (Caddy HSTS, APISIX TLS), but the internal hops Caddy to APISIX to portal to Postgres are plaintext, and the Postgres connection has no sslmode (Permify explicitly sets sslmode=disable).

Fix: Use mTLS or HTTPS upstreams inside the cluster and require sslmode=verify-full for any cross-host DB connection. Acceptable only on a fully isolated docker network.
High

E-6 · Real plaintext secrets in the local .env

Production secrets are correctly SOPS-encrypted, but lanai-portal/.env on disk holds real-looking plaintext values: JWT_SECRET, KEYCLOAK_CLIENT_SECRET, a decade-long TWENTY_CRM_API_TOKEN, and the CHATWOOT_ACCESS_TOKEN. If the disk is imaged or the file is accidentally committed, all secrets leak.

Fix: Rotate all of these, move dev secrets into SOPS like prod, and use short-lived refreshable tokens for the CRM.

Authentication and access control

High

A-1 · No two-factor authentication anywhere

There is no 2FA, OTP, TOTP, passkey, or WebAuthn for advisors or members. Keycloak has otpPolicyType: totp configured but no CONFIGURE_TOTP required action, so OTP is available but not enforced. Member auth is email plus PIN only.

Fix: Enforce TOTP as a required action in Keycloak for all advisor accounts. Add an OTP step for members (see recommendations).
High

A-2 · No account lockout on member PIN login

There is no failed-attempt counter, no lockout, and no per-account throttling. Only IP-based rate limiting protects a 6-digit PIN. A targeted account can be brute-forced from rotating IPs.

Fix: Add failed_login_attempts and locked_until columns to members; lock after N attempts and reset on success.
High

A-3 · Member IDOR: any member can read any conversation

chatwoot.getMessages is a member procedure that returns all messages for a conversation ID with no check that the conversation belongs to the authenticated member. A member can enumerate IDs and read other members' private messages.

Fix: After looking up the conversation, verify conv.memberId === ctx.member.id and return 403 otherwise.
High

A-4 · No CSRF protection with SameSite=None cookies

Production cookies use SameSite=None so they are sent on cross-site requests, yet there is no CSRF token, double-submit cookie, or Origin check anywhere. The code itself warns that ALLOWED_ORIGINS=* lets any site make credentialed requests.

Fix: Use SameSite=Lax for session cookies (only the short-lived OIDC state cookie needs None), add an Origin header check, and never allow ALLOWED_ORIGINS=* in production.
Medium

A-5 · Missing resource-level authorization on advisor mutations

Many protected procedures accept an ID and modify the record with no check that the calling advisor has any relationship to it: proposal update, send, and detail; booking status and commission; supplier update; commission markReceived and markDisputed; messaging sendMessage; task status. Any advisor can modify any of these records.

Fix: Add Permify resource checks before each mutation, or filter by createdByUserId / assignedToUserId.
Medium

A-6 · Advisor logout does not destroy the server session

Logout only clears the browser cookie; it never calls destroyAdvisorSession, so the Redis session stays valid for its full 8-hour TTL. A stolen cookie remains usable after logout, and there is no admin session-revocation endpoint.

Fix: Call destroyAdvisorSession on logout and add an admin procedure to list and revoke sessions by user.

Recommendations: what to build

Four workstreams close the gaps above. They are ordered by leverage: fix authorization scoping and audit first, because they shrink the insider blast radius for every other feature.

Workstream 1 · Authorization and audit

Per-member RBAC with Permify tuples

  • Write user:X advises member:Y tuples on member and client create.
  • Scope members.list, clients.list, communication reads, AI intelligence, and AI insights to assigned members; senior advisors and admins see all with an audit entry.
  • Add resource-level Permify checks to every proposal, booking, supplier, commission, task, and messaging mutation.
  • Make writeAudit a tRPC middleware so it cannot be skipped; capture IP and user agent.
  • Make audit_logs append-only with a hash chain and a WORM copy.
Workstream 2 · Encryption

PII at rest and document confidentiality

  • Enable pgcrypto and encrypt passport, emergency contact, family-office, dietary, visa, and NDA columns with a KMS-held key.
  • Encrypt document bytes with AES-256-GCM before S3 upload, or verify SSE-KMS on the bucket.
  • Fix the storage proxy IDOR: resolve key to document, check Permify, log every download.
  • Add WAL-G backups to encrypted S3 and test restore.
  • Enforce sslmode=verify-full for cross-host DB connections and mTLS on internal hops.
Workstream 3 · Authentication hardening

2FA, OTP step-up, and session security

  • Enforce TOTP as a required Keycloak action for all advisors; add WebAuthn for admins.
  • Add per-account lockout and a common-PIN blocklist for member PIN login.
  • OTP step-up for members on sensitive actions: document download, proposal approval, PIN change, billing changes.
  • Bind member sessions to IP and user agent; cap concurrent sessions; rotate on tier change.
  • Set SameSite=Lax on session cookies, add Origin checks, scope advisor and member cookies by path.
  • Destroy the Redis session on logout and add admin session revocation.
Workstream 4 · Data egress and hygiene

Keep data inside the perimeter

  • Remove the forge.manus.im fallback and fail fast if the in-perimeter LLM endpoint is unset.
  • Add an egress network policy allowlist for the cluster.
  • Strip secrets and PII from outbox events before lakehouse insert; never ship invitation tokens.
  • Store only digests of AI input and output, not raw dossiers; sanitise logs of email, phone, and PIN patterns.
  • Allowlist the CRM proxy to read-only, scoped paths and log every call.
Strongest existing controls to keep: SOPS and age encryption for production secrets, Caddy HSTS with APISIX TLS at the edge, local Ollama for active AI features (no data leaves the perimeter today), bcrypt-hashed member PINs, no PII in application logs, and OIDC Authorization Code flow with PKCE for advisors.
